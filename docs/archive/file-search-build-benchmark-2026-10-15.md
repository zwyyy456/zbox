# File Search 紧凑建库测量（2026-10-15）

状态：实现与测量记录，非规范文档。

## 方法

命令：`script/benchmark_file_search.sh 1000000 unique`。使用 Swift 6、`swiftc -O`，生成与上一轮相同的一百万条合成元数据（100 个目录、基本为不同 ASCII 文件名，含一条中文名称），不遍历真实文件系统。计时不包含编译。最终基准在 Xcode 测试完成后独立运行。

本轮先为原实现加入分阶段计时，再修改实现。以下是改动前、最终版本各一次完整运行；数字不代表统计置信区间。查询列使用每个进程内五次查询的中位数。`FILE_INDEX_BENCHMARK` 仅由基准脚本设置，正式 App 不输出阶段日志。

## 实现

- 增量区每块保留紧凑标量记录和 UTF-8 名称字节区；完整路径保留在哈希表中，根目录 UUID 由增量区共享。只检查状态、代次或版本时直接读取标量，不解码名称。
- 构建名称缓存也使用字节区；原名与归一化名称相同时共享偏移。ASCII 名称按字节比较，非 ASCII 使用 Swift String 比较以维持既有 Unicode 语义。
- 路径排序编号、名称排序编号、名称映射、父目录编号及倒排编号等逐文件数组改为 UInt32。构建入口拒绝超过可表示数量的输入，磁盘文件格式与 64 位偏移不变。
- 文件记录写完释放路径、名称编号、父目录等数组；名称记录写完释放名称字节区；倒排区写完释放余下逐文件数组。
- 用复用的字节缓冲区批量写入，避免每个 64 位字段经过 Data 追加路径。

紧凑存储增加了采集和名称解码开销，但排序、写入及避免无用解码带来的收益使总时间下降约 15%，建库峰值 RSS 下降约 17%。这组数据主要是 ASCII 名称；大规模非 ASCII 文件名的性能尚未单独测量。

## 验证

macOS build 与 18 项文件搜索测试通过，覆盖排序及筛选语义、Unicode 等价、空快照、UInt32 数量上限、跨 4096 条分块的并发合并、快照损坏、取消、浅扫描和真实 FSEvents 历史回放。`git diff --check` 通过。未运行 UI 测试，未进行真实百万文件磁盘遍历或外接卷人工验收。


## 后续：百万中文与中英文混合名称

命令分别为 `script/benchmark_file_search.sh 1000000 chinese`、`script/benchmark_file_search.sh 1000000 mixed`。每组包含 100 个目录，每条名称唯一：`年度项目报告-{编号}.txt` 和 `Project项目-{编号}-Report报告.txt`。这是共享长前缀、编号不同的合成数据，不代表所有语言、名称分布或真实磁盘扫描。每组前后各一次独立运行，查询各重复五次取中位数。

### 定位及修改

原先非 ASCII 名称每次排序比较都从字节区重新构造 String。两组排序分别耗时 6.96 秒、7.23 秒。改为在收集时一次生成 NFC 比较键，以 UTF-8 顺序比较；原始名称保留原字节，归一化后不同的键才增加字节存储。原名的 NFC 结果也复用于生成小写名称，避免重复工作。

Swift 源码的比较慢路径按 NFC Unicode 标量顺序比较；UTF-8 的字典序保持该顺序。参考 [Swift StringComparison.swift](https://github.com/swiftlang/swift/blob/main/stdlib/public/core/StringComparison.swift)，并用当前编译器上的测试核对组合／分解重音、重排结合符、土耳其语点号、韩文、emoji、BMP 与补充平面字符，验证映射索引的名称排序及查询结果与 Swift 规则一致。

带编号查询的大部分名称共享字符位图，之前需要解码大量不匹配名称。现在先在映射的归一化名称字节中检查查询的 ASCII 片段，只将它作为必要条件；命中仍由既有 Unicode 规则决定。这对编号等选择性较强的片段有效，纯中文查询继续走原有匹配路径。
